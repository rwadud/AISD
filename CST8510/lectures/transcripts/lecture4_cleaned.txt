The reason why you should not start with the state of the art is that they often come as publications which are trained or evaluated on standard benchmark data sets, which are often clean and well documented. The second reason is that these are more complex models, and they often require more computational resources to train and also for inference. So from that point of view, they will not be optimal, not just from the accuracy or performance point of view, and they could cause more latency.

Because of all these reasons, you should not just start with the state of the art model, but you need to find out which is the best model for your data set, which is the least complex and most efficient model for your data set through experiments. So how do you figure that out? There is this concept of a learning curve. A learning curve is nothing but this: suppose you have your data, let's say 1 million records. You create training data sets of different sizes. You create one training set at a thousand records, another at 5,000, 10,000, 50,000, 100,000 records. Like that you create training data sets of different sizes. Then for each of these sizes, you train a model. Each size is split into training and validation sets. You train the model, compute whatever metrics you want to use for evaluation. Let's say accuracy for classification. Compute that accuracy score on that size of data, both on the training data as well as on the validation data. You do this for all the different sizes and plot the curves.

What happens is that typically the curve will look like this: the red curve comes down and the green curve goes up. The reason is interesting. As the training data increases, the accuracy score on training data comes down because imagine if you only have a few data points. Any model can fit through a few data points. It always finds some optimal point which can fit through all the data points. So your training accuracy, the accuracy on training data, when you train a model and evaluate on the training data itself, the accuracy will be very high if your data set is small. Whereas when you increase the data size, the model cannot fit through all the points. It sort of finds an approximation around the data points. So you start getting slightly lower accuracy. That's the reason the training accuracy typically comes down.

Now, why does the validation accuracy curve go up? Because if you start with a small data size, the cross validation data that is not seen by the model is diverse. It could be anywhere in the space. So with smaller data, it may not be closer to what the model has been trained on. So it does not offer much generalization. But if you increase the training data size, the model is able to generalize well, because it has seen more data points. So some validation points are near the training data distribution, some are further away. So your validation score improves.

If you look at the curve on the right hand side, what is happening is that the training error is not coming down, because you still need to increase the data size. It's overfitting on the training data, even with a few hundred records. So probably if you take a size of 10,000 or 100,000, you would see it come down.

Now, the difference between the red curve and the green curve is also interesting. That tells you how much the model is overfitting. If there's too much gap between the training score and cross validation score, that indicates that you need to increase your training data. Whereas a smaller gap indicates that there is not much to leverage from further increasing the data. For example, in the case of the left curve, even if you increase training data beyond 400, it's not going to learn more. But is the model itself useful? The model itself is not very useful, because even though the gap between training and validation curves is small, the accuracy itself is very low, only about 85%. So if you train the model with 400 samples or increase samples further, eventually you are going to get only a model which is about 85% accuracy. So it's not very useful.

Whereas if you take the right curve, the cross validation score is reaching close to 1. Yes, it's overfitting because the red curve is still on top. But there's hope that if you increase more training data, then that gap will reduce, and your cross validation accuracy will improve.

So given these two models, you can decide which model to choose, and whether you need more training data, by plotting these learning curves. And you can do it very easily in scikit-learn. There is a library to plot the curve, you just have to call it. You don't need to write any code. So this is a very important concept for models and people don't often do this. You might have to do five training runs, not five models, but five different training runs with different sizes of your training data. So this is a very important concept to understand, the concept of training and validation curves.

Sometimes the curve can zigzag. That typically happens if the model gets stuck in some local optimum. But if you average over many runs, it smooths out. So sometimes it's possible to get a better score for the test data than the training data. It's possible. That would be saying that the model is performing better on unseen data than the data it was already trained on, which is counterintuitive.

The other thing you have to keep in mind when you evaluate different algorithms is the following. You typically have two types of errors: false positives and false negatives. Now, in a typical real scenario, the costs are not the same. The cost of having false positives is not the same as having false negatives.

For example, take credit card fraud detection. If you have too many false positives, what would happen? You are flagging too many transactions as suspicious. So your analyst who is investigating will have a lot of cases to investigate. Which is not a good thing, but think about if you miss. If you have too many false negatives, you say a transaction is legitimate, but it's actually a fraudulent transaction. What will happen? Too many of those and eventually a lot of customers will complain, there will be chargebacks, and you will lose a lot of money.

Similarly, if you take any diagnostic problem, detecting cancer or whatever. A false positive means what? Somebody doesn't have cancer, but you diagnose them as having cancer. So what's going to happen? You are going to have another test done for confirmation. But if you miss it, the person could lose their life.

So typically the costs are not similar. You need to look at metrics which are sensitive to this. You should not just use accuracy as a metric because it's not very sensitive to these imbalances.

The other thing you should look at when you're in an organizational scenario, when you decide on a model, is accuracy versus computational cost. For example, a logistic regression model gives 90% accuracy, whereas a deep learning model gives 95% or 92 to 93% accuracy. But it's probably five times or ten times more computationally expensive. So is it worth it, just for 2% improvement in classification accuracy, spending five times the cost?

Whereas if you take a problem like in advertising, the click through rate prediction, which is the probability that someone clicks when you show an ad, it's different because even a 0.1% improvement can make a lot of difference in revenue because you're going to show millions of ads in a day. There it probably makes sense to switch from a simpler model to a more complex one for even a small improvement.

The third factor is latency. Deep learning models are more accurate, but they take more time to produce a response, and then the customer cannot use the product effectively. So these three factors: the cost of false positives versus false negatives, accuracy versus computational cost, and latency, you need to keep in mind.

These things are not taught in the theory course, because the theory course only focuses on accuracy. They are not concerned about these practical considerations. But as an MLOps engineer or ML deployment engineer, you need to keep these things in mind because they are going to affect your organization's bottom line and revenue.

Those parameters are learned by building models on different values of the parameter and evaluating on the cross validation set and finding which one gives the best result.

Before that, we go into something called distributed training. Once you decide what algorithm you are going to use, now it comes to training. It's possible that in a lot of cases, classical machine learning models are not very memory intensive, so they will typically fit into a CPU. But if you start training deep neural networks with tens or hundreds of layers, they require very large memory. They do not fit into the memory of your GPU. So it becomes necessary to have distributed training where you distribute the training process across multiple machines.

So why do you need distributed training? Large language models, for example, have billions of parameters. A few billion parameters means a few gigabytes of memory. For example, if you take a model like LLaMA, which has 7 billion parameters, and if each parameter is stored at 32 bit or 16 bit precision, you can work out that it comes to be around 12 gigabytes of memory. But that is not enough. When you train a model, it keeps a copy of the entire parameters for computing gradients, so it roughly doubles the memory requirement. So a standard GPU with 24 GB will not be sufficient to train even a 7 billion parameter model. So you need to go to larger GPUs. Today, the standard is H100 GPUs, which have around 80 GB of memory. And for very large models, you need many such machines. Image generative models and sequence models also involve huge data and large model sizes, so they similarly require distributed training.

Now, there are different ways to take care of this problem. It's not necessarily that you need to get bigger memory machines or distribute. There's a simple technique called gradient checkpointing. This is typically applicable to neural network models. Usually all neural network models are trained using backpropagation. When you do the forward pass, at each layer you compute values and you store all the intermediate values in memory because when you are doing the backward pass, you need to use these values. You take the error, multiply by some parameter, and add to the original gradient. That's how you update the parameters. So you store all the intermediate values, which is why you are using a lot of memory.

Instead of doing that, what is proposed is that you only store values at a small number of nodes, the checkpoints. You don't store everything. Then when you need the values during the backward pass, you actually recompute them by doing the forward pass again. And you don't have to start from the very beginning. You can start from where the nearest checkpoint is.

So you randomly pick up nodes in your neural network, and only for those nodes you store the values during the forward pass. During the backward pass, for any node where you need the value, you compute it starting not from the very beginning, but from a nearby checkpoint where the value is stored. Using this, you can train models which are almost 10 times bigger in the same memory. But there's a tradeoff because you're recomputing values. However, that tradeoff is only about a 20% increase in computation time. So if you are okay with increasing the computation time by 20%, in the same hardware, you can handle models that are 10 times larger. That is the advantage of gradient checkpointing.

Then comes the actual parallelization. If you still want to distribute the training across multiple machines, there are conceptually three ways. The first is called data parallelism. The second is called model parallelism. And the third is called pipeline parallelism.

Data parallelism is easy to understand. You split the data across multiple machines. You keep the same model on all GPUs. Suppose you have N GPUs. You take the data, split it into N partitions. Each partition goes to one GPU. Then you keep the same model on all GPUs. You do the forward pass, backward pass, and accumulate the gradients. Then you share the gradients across machines, because ultimately you want one model. So you take the gradients from all the machines and do a reduction, some kind of averaging or reduction operation. Then that reduced value is used for the update. That is simple data parallelism.

Now, there are disadvantages. First of all, you are keeping the same copy of the model on each machine. The data is split, but it might not save you much in terms of memory if the model itself is large. Each machine still has to hold the full model. Also, you need to wait until each machine finishes computing to do the reduction. So the slower machines will slow down the whole process.

There are two ways of doing it: synchronous mode or asynchronous mode. If you use the synchronous mode, it will create a straggler problem because it will wait until all machines finish. If the number of machines is large, then the problem is worse because there are more chances of some machine being slower. This will waste computational resources.

This can be mitigated with load balancing. You want to make sure that all the machines have equal free memory available and equal compute available. By the way, typically only about 50% of the computation capacity of each machine is actually used. Because there are a lot of other operations: the kernel, data loading and swapping. So the actual compute efficiency is only about 50%. Because of these reasons, sometimes some machines will slow down. It may be that at that time they are swapping data between memory and storage, or receiving data from another node using the network. So the synchronous mode will not be very efficient. It creates the straggler problem because you have to wait until all N machines complete their training. To some extent, this can be mitigated using proper load balancing. As an ML engineer, load balancing and all these things need to be something you are aware of and part of your job.

In model parallelism, you distribute the model across machines. So different machines work on different parts of the model. One machine gets the first set of layers, the next machine gets the next set of layers, and so on.

In pipeline parallelism, you combine data and model parallelism. You split the model across machines, but the second machine, while working on one part of the data, the first machine can start working on the next part of the data. So initially there will be some slack, but after some time, every machine is working on some part of the data. This is more optimized than either doing pure data parallelism or pure model parallelism.

But even in pipeline parallelism, there is some slack because later stages have to wait for earlier stages to finish. There is a sequential dependency, though it is much smaller than in pure model parallelism. Because unlike in data parallelism, each machine is only working on a portion of the data and a portion of the model, the idle time is much smaller, but there is still some slack.

Then there is a third approach called Fully Sharded Data Parallelism, or FSDP, which takes care of that. In model parallelism, you split the model sequentially, so GPU 0 gets layers 1 to 10, GPU 1 gets layers 11 to 20, and so on. The layers are split sequentially. And that's why when you do the forward pass, there's a dependency. The first machine has to compute before it goes to the next machine.

In FSDP, instead of doing it this way, from every layer, you sample a subset of parameters, then distribute them. So from layer 1, you take some set of parameters and give them to GPU 0, take another subset and give them to GPU 1, a third subset to GPU 2, and so on. So every GPU has some parameters from every layer. It's not a sequential split. The distribution of the model is more random.

In model parallelism, you are slicing the model layer by layer. In FSDP, you sample some parameters from each layer and distribute them. So every GPU has some set of parameters from every layer. That's the difference.

What happens with this is that each GPU already has a subset of parameters. Then it calculates the gradient on a subset of data, a microbatch. The data is also split. Then when it needs to update, it borrows the gradients from other GPUs, but only for that particular layer. For example, for layer 1, some parameters are on this GPU. The remaining parameters are distributed across different machines. To completely update that layer, you need all the parameters of that layer. So all the necessary parameters for that layer are acquired from other machines through an all-reduce operation. Then once it does this, it takes all the parameters required for one layer, does the computation, then moves on to the next layer.

The main advantage is that in this model, the entire model doesn't have to fit on one GPU. In data parallelism, you keep the entire model on each GPU and split only the data. So if the model doesn't fit in memory, it doesn't work. But in FSDP, you're only keeping part of the parameters for each layer on each GPU. So every GPU has parameters from all layers, but only a subset of parameters. Therefore, the memory requirement is much smaller. But after doing the reduce, scatter, and gather operations, you get the same information. Every GPU has the sum of all the gradients from all the data points. It just reorders the way you compute. It's a very clever way of doing it.

This was invented by Facebook. FSDP stands for Fully Sharded Data Parallelism. There is also a nice open source library called FairScale. FAIR stands for Facebook AI Research. There is also a PyTorch native implementation available. Today, the state of the art for training uses something called 3D parallelism, which combines multiple forms of parallelism in different dimensions.

AutoML is a kind of fancy term that comes in two varieties. One is called soft AutoML, which is hyperparameter tuning. The model architecture is finalized, the algorithm is chosen, but there are some parameters which cannot be learned from data directly. They are not learned by minimizing the loss function. Those are called hyperparameters. Hyperparameter tuning is the final step of your model development, and you do it through an automated process. That is the soft AutoML part.

Then the hard version of AutoML is where you don't even know the architecture. You probably know it's a neural network, but you don't know how many layers, how many neurons in each layer. If it's a convolutional neural network, what should be the size of the convolution operator, what kind of loss function to use, what kind of activation function. All of that is unknown. That is where the real AutoML comes in. It's called neural architecture search.

For hyperparameter tuning, you can do it multiple ways. The simplest way is grid search. If you have two or three hyperparameters, for each hyperparameter you create a grid. One hyperparameter goes from 0.1, 0.2, and so on. The other hyperparameter similarly. Then you systematically explore every point in this grid. But that is extremely expensive because as the number of hyperparameters increases, the grid search grows exponentially. There are exponentially more possibilities.

So instead, what is recommended is random search. In your hyperparameter space, instead of going through that space systematically, you randomly pick up some points and do evaluations. You randomly pick a point, train a model, measure the performance on the validation data set. If that performance is better than the best model so far, you replace it with that model. It's possible that after you go through all these randomly sampled points, your final model performance is not great. Then you do another round of random sampling. The advantage is that this is linear in cost. You can keep doing it as long as you want. Each time you're only evaluating a single set of parameters. Whereas grid search grows exponentially.

So grid search is almost never used in practice unless it is a one parameter or two parameter situation. The moment it becomes more than two parameters, always go for random search.

Now, there is an even better method called Bayesian optimization. In Bayesian optimization, you actually build a model on top of the hyperparameter optimization itself. You build a model which will predict what is the best value of the hyperparameters. You're modelling the accuracy of the model as a function of the hyperparameter values. It gives you not just the predicted value of your accuracy, but also the confidence interval.

You create this kind of model using a Gaussian process. You start with a few randomly sampled values, and you actually evaluate the real model at those values. So you have a hyperparameter space, you randomly sample some N points. Then for each of those points, you compute your actual model accuracy. Then you use this as training data for the Gaussian process model.

This Gaussian process model will predict your model accuracy and the confidence of the accuracy. Then you do exploration and exploitation. You take different values of your hyperparameters, put them into this surrogate model, and see what is the predicted accuracy. You look at regions where the accuracy is predicted to be high. But you also check regions where the confidence is low, because those are areas not yet explored and could potentially contain good values.

Then you take those candidate values, actually put them into the real model and train it. You get one more data point. Then you update your Gaussian process model. You keep doing this. You explore different regions of the hyperparameter space using this Gaussian process model, which predicts the expected accuracy of your original model for a given set of hyperparameter values. Then you take regions where the confidence is high and the accuracy is high, and also regions where the confidence is low, because those need exploration. Then you actually take those points, do an experiment with the real model, get the accuracy value, and update your Gaussian process model.

This is surprisingly very fast. It will give you good hyperparameter values within about 10 to 12 iterations. Because the Gaussian process is a simple surrogate model, you're doing a kind of meta-model optimization. This is what is currently used in practice for hyperparameter tuning of SVMs, random forests, gradient boosted trees, and other models.

The final thing is neural architecture search, also called NAS. The essential idea is that you first create a search space. The search space consists of the building blocks of the neural network: the number of layers, the kind of convolutional operations like 3 by 3 convolution, all possible kinds of convolutions, all possible connection types, all possible activation functions. This is your search space, because you are going to build different architectures by taking different combinations of these building blocks.

Then you need a search strategy. How do you do the search? There are different kinds of strategies. A simple strategy uses exploration and exploitation. 80% of the time you do exploitation. For example, you know that convolutional architectures work well for object detection. So 80% of the time, you experiment within that architectural family, changing kernel sizes, adding or removing connections, trying small variations. 20% of the time you do exploration. You try completely different kinds of networks, maybe a recurrent network, maybe something like an LSTM, something completely different.

Then you need a performance estimation strategy. You typically do some kind of cross validation.

What are the different search strategies? The first is reinforcement learning based. You have a controller model that acts as an agent. That agent proposes a model description. Then the model that the agent described, you actually implement, train it, and measure the performance. Then the performance, let's say accuracy, is given as a reward back to the agent. You keep doing this. The reinforcement learning agent keeps optimizing, and eventually it converges to a good architecture.

There's an example called NASNet, which is a neural architecture search for an image classification problem where it was shown that they beat human designed models. The only thing is that they had to run about 800 GPUs for four months. It's possible, but very expensive.

The second way is called evolutionary methods. You start with random models. Each model you implement, measure the performance, and you kill all the models with bad performance. Then you mutate the good models. Mutate means you change the number of layers, or the number of neurons in each layer. You repeat this process of selection and mutation, and eventually you get a good model. There's an example called AmoebaNet. But again, it's computationally expensive because every iteration you have to build and evaluate these models.

The third method is called differentiable or gradient based methods. Here, what they do is create one super model that contains all possible candidate operations. Each candidate operation in the search space is weighted. The weights are in the form of a softmax function. Now this function is differentiable. Then you can do gradient descent on these weights and find the values of the weights which sort of best represent the optimal architecture. So you find the best architecture using gradients rather than trial and error.

This is actually the most popular way of doing neural architecture search now. Instead of running for four months on hundreds of GPUs, you can do it in a few hours. The computational savings are enormous compared to the reinforcement learning or evolutionary approaches.
