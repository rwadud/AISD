Now, how do you reduce latency? You can do it through three approaches. The first is that you make your code very optimized. A lot of latency happens because you are not doing proper parallelization, multi-threading, or you are probably using the wrong data structures, or you are using a loop instead of using a recursive algorithm. A lot of optimization you can do at the code level to reduce latency. That is number one. Then the easy, low-hanging fruit is to make your hardware faster. You bring hardware which has faster CPUs or GPUs. But that may be more expensive. Then there is another thing you can do, which I will talk about later, which is that you can compress your model. Your model, in spite of your code being highly optimized, when it goes to the model, the model has to process that request. If your model has a lot of neural network layers, it has to go through a complete forward pass to make the prediction. If you make the model more compressed, that also reduces your latency. So these are the three ways of reducing latency.

The reason a compressed model gives better performance is that the memory requirement is reduced. When we say compressed model, it just means that instead of using 32 bits per weight, which is typical, you use a lower representation, 16 bits. Today even 4 bits are used in neural networks. If you use 4-bit representation, memory is reduced by almost one-eighth. So you can load a model on much smaller hardware, or a bigger model can be loaded on the same hardware. That is the advantage.

If you compress the model, it runs faster. Not only that, you can deploy them on edge devices. They can run on your laptop. That is what everyone is working on. So what Ollama does is that it first of all runs on C++. It uses a C++ based backend. Then it loads a compressed version of the model. That is why you are able to run LLMs from your laptop.

There is a website, Awesome Open Source, that lists a lot of projects on model compression.

How do you compress the model? There are four ways of compressing models. The first is called low-rank factorization. The second is knowledge distillation. The third is pruning. The fourth is quantization. Let us look at what each of these is.

Low-rank factorization typically works well with GPUs, when your model is a neural network model running on a GPU. What you essentially do is, for example, in convolutional neural networks, you use convolution filters, which are typical tensors. They will have some dimensions like a tensor with dimensions H by W by C. You can replace that with a smaller filter by reducing the depth.

For example, this is an actual example of AlexNet. Everybody has heard of AlexNet. That is one of the main deep learning models, which was created by Geoffrey Hinton and others. That is the first model built using deep learning that got very high accuracy. AlexNet uses large convolution filters. You can replace them by one-by-one convolution filters, and you get a compressed version. The reduction is about 50% in parameters, but the degradation in performance is only about 5%. So essentially, you replace high-dimensional tensors with lower-dimensional ones. You find the low-dimensional tensors by doing a low-rank factorization. Any big tensor, any big matrix, you can write as a product of smaller matrices. If you have an M by N matrix, you can decompose it into an M by K and a K by N matrix, where K is very small. So use that method to find your lower-rank representation. That is the idea of LoRA.

The second method is knowledge distillation. Knowledge distillation is what you are actually seeing in a lot of these Llama or Gemma kind of models. Gemma, for example, is a model where they have taken Gemini and used Gemini to teach a smaller model. That is how you train the smaller models. It is called knowledge distillation. The idea is that instead of directly training a smaller model, you use a bigger model, and that model trains a smaller model. This is the student-teacher model training approach. It is like transfer learning. You use a bigger model and that model trains a smaller model. It improves the generalization.

The reason is like this. When a teacher tells you something rather than you reading the book, the teacher sort of abstracts things and tells you. The teacher tells you the concept directly, whereas when you read a book, you cannot get that concept directly. So when you use a larger model to train a smaller model, the training becomes more effective because of the way the larger model summarizes things.

As an example, the BERT model. The BERT model, everybody knows, is the first transformer-based model. Bidirectional Encoder Representations from Transformers. That is the first well-known model based on Transformers, produced by Google. At one time, it was kind of the only model available and was like a workhorse for NLP. But the BERT model was heavy and it was difficult to deploy. So they produced a reduced model through knowledge distillation, through teacher-student training. They produced a model called DistilBERT, which reduces size by more than 50%. But still, the accuracy degraded only 3%. Then DistilBERT became the standard trade-off. Just for 3% of accuracy loss, you are getting a model which is half the size or less. And it is 60% faster. So people started using DistilBERT. This is a classical example of knowledge distillation where you use a bigger model to train smaller models.

These days, a lot of models do this. Even Llama. There is actually a Llama 405 billion parameter model that was used to train the smaller Llama 3 models. Similarly, Gemini is used to train Gemma. And many open-source models are trained using GPT-4 outputs. So that has become a standard these days for producing smaller models.

Why is knowledge distillation better than directly designing and training a small model? Because when you directly train a model, every model has a capacity. If you take a model, let us say a 3 billion parameter model, and you train with a lot of data, beyond a certain data set size, it does not learn much. I plotted a learning curve the other day. A learning curve is a curve where accuracy is plotted against training data size. It sort of saturates at some point.

So what happens is it cannot learn a lot of things. Suppose I have all the Wikipedia articles and all the online artifacts. I have a massive data set. Let us say 3 trillion tokens. I start training a 3 billion parameter model with that. By the time I probably finish one-tenth of that training data, it reaches capacity. It does not learn anymore. So I have no way to teach all these subjects to a small model. Instead of that, I have Gemini, which is a bigger model. I can train that with that data set. Then I sample from that Gemini, let us say 100 billion samples of that, and train the smaller model using that. Then it covers the content. Because when I sample the data from Gemini, it will be done in such a way that it sort of abstracts the concepts that the training data has. It is exactly like a teacher teaching a student versus the student learning directly on their own.

So it improves generalization. It also reduces overfitting because what might happen when you directly train the model is that you have a lot of duplicated data, noise, and all that kind of thing. With knowledge distillation, the smaller model does not learn from the noise. When a real teacher teaches, they have understood the concept. They will teach correct things, rather than you learning from random or unreliable sources.

As for how the knowledge is transferred from the bigger model to the smaller model, whether it is the training data that is transferred or the model structure, I think a lot of it involves both. They take the architecture from the bigger model, but they fine-tune it. For the fine-tuning, they take the data from the teacher model. There are multiple ways of doing it. But a lot of it is that they take the initial architecture. The model weights cannot come directly from the bigger model because the smaller model has fewer parameters. Gemini is a much bigger model with a large number of layers. So what they probably do is take some portion of it, some layers. But then the teacher labels the training data. That is, I think, the most important thing.

Now, the third technique for model compression is pruning. This idea essentially came from decision trees. When you build decision trees, you start from the root node and split on a variable at each level. You decide how to split the data set. The way decision trees work is you have a data set. You take a feature and based on that feature, you split the data set into two. For example, let us say your data set contains a population of people with attributes like age, gender, income, and medical status. You take a variable and split the data set. You decide which variable to pick based on which variable will give a better entropy reduction as a result of splitting. You experiment with age, then you experiment with income, then gender, then marital status. Let us say you found out that the best variable to split on is age. So that is the first split in the decision tree, based on age, split into two. Then each of those two buckets, you further split on another variable. Again, you find out which variable to split on for better entropy reduction. You keep doing this till you get leaf nodes where only probably one class remains. That is ideal.

The problem with decision trees is that a lot of times they overfit. Then what you do to avoid overfitting is pruning. You remove some of the leaves. That same idea, you take it to neural networks. You sort of prune by setting weights of neurons to zero. You train the model using backpropagation. Then after doing that, you randomly pick some fraction of your weights, typically the smaller weights, and set them to zero. That is called pruning in the context of neural networks. And there are cases where you can genuinely reduce the number of parameters even up to 90% and still not lose accuracy by much, because neural networks are highly overparameterized. Because you have nonlinear functions and a large number of parameters, the network typically overfits considerably. So pruning is done. Pruning and batch normalization are two things done to reduce overfitting.

The fourth technique is quantization. Quantization is straightforward. You use a lower bit representation for your weights. Typically, with single precision, you use 32 bits. You can use half precision, which is 16 bits. Typically, models are trained using half precision these days. But at the time of inference, you reduce it to 8 bits, and these days even 4 bits. You can go to 4 bits without sacrificing your accuracy much.

Through the tokenization process, a sentence is transformed into a numerical vector, and we have many examples shown here. In our earlier attempts at optimizing, we were trying to batch our inputs. As shown in the first box, they were fixed shape. We were zero-padding our input vectors of different lengths so that they would have the same length so that we could pass them together as a batch into DistilBERT. We thought that batching up these requests was going to be more efficient. But as it turns out, it was actually much easier and faster to just use a batch size of one. And that is what is shown below, the dynamic shape inputs. Since we are dealing with a real-time, low-latency application here, this is also much more natural. Once we did this, we no longer had zero-padding because the input vectors are all their natural length when your batch size is one. This shortened our inputs a lot and we got a big speed improvement from doing this.

Our third example of less is more that we want to share is quantization. This was actually what provided us with our biggest gain and it is the biggest part of why we could achieve a 30x improvement over our first BERT baseline. With just the main three optimizations you see here on this chart, we got all the way down to 10 milliseconds of latency on average, and over 3,000 requests per second on a 32-core machine.

Quantization involves improving the efficiency of deep learning computations through smaller representations of model weights. For example, representing 32-bit floating point weights as 8-bit integers. The specific quantization technique we leveraged for our DistilBERT model is called dynamic quantization. This technique involves quantizing weights after training, as opposed to quantizing during training. And this turns out to be much easier as well. One of the really cool things about this quantization improvement is that in PyTorch, we can do it in just one line. We are showing here the one-liner to transform the float 32 weights in the DistilBERT model into INT8 so that at inference time, these smaller weights are actually used. One quick note here too: this is also a change, just like DistilBERT, where we had to give up a little bit of our accuracy in order to get the big speed gains. This is a normal kind of trade-off that you have to think about as you are scaling up your models.

Here is just a view of what things look like under the hood after you quantize your DistilBERT model. It is exactly what you would expect from the one-liner, which is that the linear layers in the original model are replaced with dynamic quantized linear layers, where the operations, like linear operations, are done in INT8 in order to get better performance.

So at this point, we have talked about the three biggest keys to scaling BERT for inference: smaller models, smaller inputs, and smaller weights. But we have two more really important ones to share, and they are also very easy.

The next one is not rocket science. We also got a big boost in our throughput through simple caching. This is an example of less is more as well, because now we are effectively sending a smaller number of requests to our DistilBERT model. The idea is, if many of your text inputs are the same, there is no reason really to bother your busy deep learning model with responses that it has already calculated. Some of our text classifiers had their throughput increased by over 2x due to caching. So this is an easy win, but it depends on your distribution of text data.

The last example of less is more is another simple one, and that is thread tuning. This one is so critical that all the results that you saw earlier are not even possible without doing this on CPU. Or at least that was our finding. The critical thread tuning is shown on one line above. The idea is that when you have lots of processes running a BERT model on the same machine, which is probably almost always the case when you are running at high scale like we have, you want to make sure that all those processes play nice with each other. In this case, we did better by limiting thread-level parallelism for each of these processes. In particular, limiting each process to just one thread. To use a footrace analogy, as you can see in the picture below, it is easier for all the runners, analogous to processes, to finish the race if they stick to one lane rather than trying to run in multiple lanes. This was really key, and in fact, this is probably where you should start before running any benchmarks and starting to scale your systems.
